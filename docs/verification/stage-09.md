# 能力恢复与重新发送验证记录

日期：2026-11-09。对应[实现计划](../plan/V1.0.0/09-recovery-resend.md)、P-03、T-10、AC-17、AC-34、AC-37、AC-38。

实现与自动化验证已完成。按用户安排，真实耳机、外放、默认设备及云端恢复演示稍后验收；完整主窗口、悬浮可见性与设置页继续在对应阶段整合。

## 实现与确认

- 处理器同步 `on_error` 读取 Pipecat 已形成的错误分类与可用性，记录模型、ASR、System One、TTS 和录放音服务来源，关联实际输入与回复。运行时只把受影响的处理中回复标成失败，保留已展示内容及先前完成的消息。
- ASR、System One、TTS 及音频对象不可用后，旧 worker 沿原生 CANCEL 结束。用户继续发文字时，先等待旧对象清理和最终上下文提交，再创建文字对象。清理期间已接收的新输入由同一消费者继续处理，语音保持不可用状态。
- 每个执行对象的事件回调绑定自身归属；新对象接管后，旧回调无法继续修改消息或能力状态。已失败回复的迟到文字也不会恢复流式状态。
- 用户确认的恢复规则为：立即打断正在生成的文字，保留并提交已有片段，然后关闭旧对象并创建新语音对象。恢复使用本次启动的有效配置和当前 Windows 默认设备，成功回待唤醒；后续仍由用户唤醒和提问。
- `resend_text(user_message_id)` 从后台原消息读取正文，沿现有文字发送路径追加新的用户消息与助手回复。仅失败文字用户消息提供此入口；旧消息、旧错误、回复片段及输入框草稿继续保留。
- 主窗口显示故障与恢复结果；可见悬浮卡片显示当前语音问题、已有回答和恢复按钮，附和继续归属原问答；托盘显示语音或模型不可用并按能力启用恢复入口。错误事件保留已有窗口可见性，手动隐藏的悬浮组件继续隐藏。

修改 `.env` 后重启应用生效，恢复按钮使用当前进程配置。

## 错误与状态映射

| 失败来源 | 当前回复与记录 | 能力和后续操作 |
| --- | --- | --- |
| 模型临时错误，例如 HTTP 503 | 失败原因绑定当前回复，保留已有文字 | 模型仍可用，用户重新提问或对失败文字点击重新发送 |
| 模型永久错误，例如 HTTP 401 | 保留当前失败与历史记录 | 停止生成，显示检查模型配置并重启应用的原因；窗口和历史继续可访问 |
| ASR / System One | 关联受影响的输入或回复，保留已展示片段 | 语音不可用；模型可用时文字继续接续，语音由用户主动恢复 |
| TTS | 失败状态及已展示文字保留 | 文字继续可用，恢复成功后等待新输入 |
| 默认设备或音频流失效 | 保留具体设备错误及受影响回复 | 释放旧音频资源，恢复打开当前默认设备 |
| 恢复时设备打开失败 | 显示具体失败原因，`voice_recovery=failed` | 文字按模型条件可用，可再次请求恢复 |
| 语音配置缺失 | 已保存记录持续可读 | 模型配置有效时文字继续可用 |
| 模型配置缺失，或模型和语音配置均缺失 | 已保存记录持续可读 | 禁用发送，显示缺失配置原因 |

完整状态快照新增：

- `last_error`：最近一次处理器或设备错误的 `service`、`category`、`permanent`、`message`、`reply_id`、`source`；没有受影响的处理中回复时关联为 `null`。
- `voice_recovery`：`idle`、`running`、`succeeded`、`failed`。当前语音可用性和当前故障仍由 `voice_status`、`voice_error` 表达。

DeepSeek 的 `AsyncOpenAI(max_retries=0, timeout=60)` 沿用现有配置，Pipecat 超时重试保持关闭；运行时和重新发送入口均由用户操作发起后续请求。恢复不会重复旧轮次的模型、TTS 或 ASR 请求，回待唤醒后 ASR 继续关闭。

## 自动化结果

`tests/test_recovery.py` 新增 13 个参数化场景，使用本机 HTTP/SSE/WebSocket 服务与内存音频 transport，运行实际 SDK、语音适配器、Pipecat 聚合、错误分类及取消流程：

1. ASR、System One、TTS 分别失败，检查具体服务、回复片段、文字接续和窗口可见性。
2. 恢复采用新的默认录放音端点，回待唤醒并保持原问题、旧片段及模型上下文；再次唤醒才打开 ASR。
3. 模型 503 维持可用，模型 401 禁用生成，均没有自动重复请求。
4. SSE 返回片段后断开，失败文字重新发送追加新消息，旧消息和片段保留，新回复只输出文字。
5. 文字生成过程中恢复语音，检查片段提交、`interrupted` 状态及旧语音/文字对象迟到回调隔离。
6. 新默认设备打开失败后保留具体原因，用户再次请求恢复可成功。
7. 缺少语音、模型、两者配置三种组合下，重启后保留真实已保存记录；有模型时文字正常接续。
8. 语音激活与待唤醒期间分别构造执行错误和延迟清理，清理期间接收的新文字均正常完成，语音能力保持错误状态。
