## 1 产品定位与版本目标

V1.0.1 将小博建设为能够持续交流、调度本地任务并恢复执行的桌面 Super-agent。用户通过语音或 UI 文字与同一个主 Agent 交流；普通聊天由主 Agent 回答，具体工作由拥有独立上下文的 Worker 执行。

本版架构主要参考 DeepSeek 官方组织发布的 `dsh-superagent-prototype`，采用事件接收、任务关联、主 Agent 调度、独立执行和持久化恢复的职责划分。官方原型的 Ticket 表示工作，Assignment 表示一次执行安排；任务可以跨执行器重建继续存在。[官方领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/001-domain.md)、[官方执行机制](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md)

本项目的主 Agent 同时负责日常对话和任务调度，这是面向桌面语音交互已确认的产品选择。用户看到对话、任务及其结果，内部执行会话由程序管理。

版本目标形成以下闭环：

1. 用户通过语音或文字提出本地操作要求。
2. 主 Agent 理解要求，创建任务或将补充交给已有任务。
3. Worker 调用明确工具和已接入控件，报告真实进展、问题和结果。
4. 用户继续交流、查询进展，或明确控制某项任务。
5. 应用保存任务和执行记录，重启后核对已产生的结果，再继续未完成任务。

| D-27 | 结果播报被打断 | 界面保留结果。用户询问或要求继续时，再简要播报 |

| D-29 | Worker 的历史读取范围 | 按需读取本任务、来源对话和主 Agent 提供的相关引用 |

| D-31 | 共享资源冲突 | 同一文件或窗口上的冲突动作依次执行，各任务中满足依赖的其他步骤可以继续 |

| D-35 | 后台任务提问 | 在聊天区和任务详情显示可回复的问题。语音任务在语音激活且空闲时可简短询问，待播报的问题优先于结果 |
| D-36 | 任务控制入口 | 卡片按当前状态显示暂停、继续或取消。任务详情提供完整记录和失败后的重试 |
| D-37 | 补充生效时机 | 保存用户补充，当前步骤结束后在下一步采用。扩大任务范围前由主 Agent 向用户确认 |
| D-38 | 任务记录保留 | 随对话历史长期保留任务状态、执行过程和产物引用。生成的文件保存在用户指定的位置 |
| D-39 | 退出等待 | 等待不可取消步骤时显示所属任务和当前步骤，并允许撤回退出请求 |
| D-40 | 撤回退出后的任务恢复 | 恢复派发。核对结果后自动接续因退出而中止的任务，仍在执行的步骤继续。用户主动暂停或取消的任务保留原状态 |
| D-41 | 已结束任务收到新要求 | 查询结果时使用原任务。用户明确要求执行新操作时，新建与原任务关联的任务，保留原任务的结束状态。要求含糊时先澄清 |
| D-42 | 一条指令的任务划分 | 同一目标下相互依赖的步骤归为一项。主 Agent 可拆分能够独立交付的目标，并告知用户拆分结果 |
| D-43 | 任务反馈的输入来源 | 后台任务结果和待回答问题按任务创建时的输入来源处理。实时追问的答复按当轮输入来源处理 |
| D-44 | 重发任务请求 | 「重新发送」先查原消息关联的任务。任务已保存时展示状态，确认尚未创建时才重新处理原请求 |
| D-45 | 暂停或取消意图的恢复 | 先保存用户意图，再处理在途步骤。重启后核对该步骤并按原意图完成暂停或取消。核对期间停止后续派发 |
| D-46 | 本机动作的结果保存 | 改变本机状态的动作完成后，先保存实际结果，再派发该任务的下一步。保存失败时暂停该任务并报告原因，恢复时先核对动作结果 |
| D-47 | Worker 工具调用范围 | 工具按用户已明确的任务目标、对象及路径执行。读取的文件、历史引用和工具结果作为任务资料，扩大操作范围需经主 Agent 向用户确认 |
| D-48 | 待用户问题的回复归属 | 回复关联到具体任务和问题。聊天或语音中的回复归属不明确时先澄清，待用户任务获得有效答复后按并发上限重新调度 |
| D-49 | 最后一步收到补充 | 保存补充。原结果已生成且任务没有后续步骤时，告知用户原结果，明确的新增操作按关联任务规则处理 |
| D-50 | 主对话忙碌时收到任务结果 | 先保存并展示结果。主对话空闲后检查原语音交互是否仍激活，再决定播报。等待期间回到待唤醒或语音结束时保留未读，由用户查询或要求播报 |

## 3 现有实现与本版接入位置

当前 `Conversation` 将模型、工具、用户/助手聚合器和语音处理装配在同一条 Pipecat 流水线中。`PipelineWorker` 负责该流水线生命周期。新文字输入会广播原生打断并等待流水线提交，语音模式同时协调 ASR 与旧输入清理。依据：`src/voice_super_agent/conversation.py` 的 `Conversation.__init__`、`send`。

当前模型工具是 `history_search`、`history_read` 和语音模式的 `end_voice`。桌面桥接已有窗口显示/隐藏、语音控制、交互设置、历史浏览和重新开始等入口，业务 Worker 工具需要明确接入。外部项目控件目前尚未接入。依据：`conversation.py`、`desktop/host.py`、`runtime.py`。

首批本地业务工具由内置 MCP 服务提供，供小博自己的 Worker 调用。应用窗口动作经现有桌面宿主调度到 GUI 线程，任务状态和恢复由小博管理。MCP 接入为 V1.0.1 的新增工作。

现有 SQLite 保存展示消息、模型消息、工作窗口及交互设置。后台任务、各次执行、待处理任务输入和任务恢复信息需要新增数据表示。依据：`src/voice_super_agent/memory/store.py` 及现有迁移脚本。

本版需要将业务任务生命周期从主对话及语音流水线中分离。STS 继续作为识别、语义附和、接管、轮次和播报的流程依据，具体语音规则参见 [V1.0.0 第 5 节](V1.0.0.md#5-sts-语音流程依据与迁移指示)。

## 4 领域概念与职责

| 概念 | 本项目中的含义 | 产品要求 |
| --- | --- | --- |
| Source / 输入来源 | 本版的桌面语音与文字输入 | 保存消息来源，使输入能接入统一的处理和反馈流程 |
| Trigger / 输入事件 | 一次正式输入或相关运行事件 | 保留事件标识、时间和关联信息，处理重复投递 |
| Thread / 关联线索 | 组织输入与任务之间的连续关系 | 将明确指向任务的补充和查询关联到该任务。需要执行新操作时可创建关联任务，归属含糊时向用户澄清 |
| 主 Agent | 日常交流与任务调度入口 | 创建和关联任务、查询状态、传递补充与明确控制，组织用户反馈 |
| Task / 任务 | 用户要求完成的工作，对应参考架构中的 Ticket | 持有目标、范围、状态、来源、补充输入、执行记录和结果 |
| Execution / 本次执行 | 某个 Worker 对任务的一次执行安排，对应 Assignment | 保存实际开始、结束、进展、错误及恢复信息，归属于稳定的任务 |
| Worker | 持有独立任务上下文的执行角色 | 调用任务所需工具，处理补充，报告进展、待用户问题和结果 |
| 工具与控件动作 | 应用明确开放给 Worker 的本地能力 | 首批业务工具通过内置 MCP 服务提供。接收明确参数，返回真实结果，表达取消和结果核对能力 |
| 反馈 | 面向用户的回复、任务问题或结果 | 关联原任务，按已确定的界面和语音规则呈现 |

主 Agent 和各 Worker 分别使用有限的模型工作窗口。Worker 按需读取本任务、来源对话和主 Agent 提供的相关引用，完整原文通过稳定标识关联。DeepSeek 原型提供了沿事件、Thread、Ticket 与执行历史读取的资源接口。[官方架构与回读接口](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/007-architecture.md)

## 6 主要交互流程

### 6.1 日常对话与新任务

主 Agent 接收正式用户输入，结合主对话和必要任务信息判断意图。普通聊天直接回答；本地操作要求进入任务创建流程。任务需要的具体对象、参数或范围不明确时，先取得必要信息。

同一目标下相互依赖的步骤归为一项任务。一条消息包含多个可独立交付的目标时，主 Agent 可以拆成多项任务，并告知用户创建了哪些任务。新任务记录创建时的输入来源，供后续反馈使用。

任务记录与待执行安排保存后交给 Worker。Worker 的进展、待用户问题和结果关联回任务。主 Agent 的输入接收与后台执行并行推进。

主 Agent 按任务依赖及用户要求决定哪些工作同时执行、哪些等待。默认并发上限为 2，可在设置中修改，设置保存后用于新派发。调低上限时，在途任务继续执行，运行数低于新上限后再派发。已暂停和待用户的任务释放执行名额。同一文件或窗口上的冲突动作依次执行，满足依赖的其他步骤可以继续。

打开应用时，根据用户给出的名称或明确路径定位本机应用。目标重名或信息不足时，请用户明确目标。找到已有可用窗口时显示该窗口，其余情况按明确目标启动应用。

文件工具按用户指定的本机路径查询目录、读取支持的文本内容或生成新文件。目录和文件名查询覆盖目录中可访问的各类文件，内容读取与生成支持纯文本、代码、Markdown、JSON 和 CSV。目标路径上已有同名文件时，保留已有文件，提示冲突并请用户指定新名称。

Worker 的实际工具调用以用户已明确的任务目标、操作对象和路径为准。文件正文、历史引用和工具返回的文字作为任务资料。若完成任务确需操作用户范围之外的对象或路径，Worker 通过主 Agent 询问，取得用户确认后再执行。

内置 MCP 服务随小博启动与退出，主窗口隐藏到托盘时继续可用。工具接入失败时显示具体原因，未受影响的能力继续工作。

### 6.2 补充、纠正与归属

用户可以通过语音或文字补充已有任务。明确指向任务的输入保存到对应任务，当前步骤结束后在下一步采用。归属有歧义时向用户澄清，涉及扩大任务范围时先由主 Agent 向用户确认。

对已完成或已取消的任务，用户查询时读取原来的状态和结果。用户明确要求执行后续操作时，新建与原任务关联的任务，保留原任务的结束状态。无法判断是查询还是新操作时，先向用户澄清。

在最后一步执行期间收到补充时，保存补充及其对应任务。若该步骤已经生成原结果且任务没有下一步，告知用户原结果已生成。明确的新增操作按 D-41 创建关联任务，目标有歧义时先澄清。

### 6.3 语义附和和播报接管

播报期间仍由 STS 的 System One 路径判断附和与接管。附和保留现有展示和上下文规则。确认接管后，主对话接收正式输入，当前播报停止，业务任务按自己的状态继续执行。

模型正在生成、尚未播报时，新语音沿既有原生用户轮次通路处理。主对话打断和业务任务暂停、取消分别作用于各自生命周期。

### 6.4 暂停与继续

收到明确暂停要求后，保存用户的暂停意图并停止派发该任务的后续步骤。支持取消的当前动作立即停止。其他动作等待当前步骤结束，期间展示“正在暂停”。实际动作停止或完成后，保存执行位置及结果并进入“已暂停”。

任务进入已暂停状态后释放执行名额。继续命令将对应任务重新交给调度。各工具在动作取消后如何核对部分结果，由技术设计验证。

应用和文件工具统一采用 MCP，任务状态以实际业务动作状态为依据。MCP 服务端可以忽略无法取消或已经完成的请求。收到取消通知后，任务根据工具是否实际停止或完成，更新暂停或取消状态并保存结果。[MCP 取消规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation)

### 6.5 取消

收到取消要求后，保存用户的取消意图并停止该任务的后续执行，保留已经完成的操作、输出和执行记录。当前动作仍在执行时显示“正在取消”，实际停止或完成并保存结果后显示“已取消”。

### 6.6 重启恢复

应用重启后读取任务及执行记录。已暂停或已取消的任务保留原状态。在途的暂停或取消意图按 D-45 处理。其他待执行或因应用退出、异常中断的任务核对结果后自动继续。已失败的任务按第 6.9 节等待用户继续或重试，待用户回答的问题保留在任务中。

已完成且核实的步骤保留结果，从确定未完成的部分接续。无法确定前次动作结果时，保存已有证据并请用户确认该步骤，其他状态明确的任务继续。各工具的核对依据在设计和验收中落实。

任务处于“正在暂停”或“正在取消”时发生中断，重启后按已保存的用户意图处理。只核对中断时的在途步骤，核对完成后记录为对应的“已暂停”或“已取消”。结果不确定时保留停止意图并等待用户确认该步骤，核对和等待期间停止后续派发。

### 6.7 异步反馈与语音空闲

后台任务的结果和待回答问题按创建任务时的输入来源处理。用户实时查询或追问时，答复按当轮输入来源处理。语音发起的任务即使后来通过文字跟进，异步反馈仍按语音任务规则呈现。

任务结果持续保存并在界面展示。语音任务在语音交互已激活且主对话空闲时播报简要结果。回到待唤醒后，结果在界面展示并标记未读。文字任务的异步结果在界面反馈。结果播报被打断时，等用户询问或要求继续再播报。

语音任务结果在主对话忙碌时到达，先保存并展示。等主对话空闲后，在播报前再次检查原语音交互是否仍激活。等待期间语音结束、超时或因故回到待唤醒时，结果留在界面并标记未读，之后由用户查询或要求播报。

任务需要用户回答时，在聊天区和任务详情展示可回复的问题。语音任务在语音交互激活且空闲时可以简短询问。有多条反馈待播报时，先询问待回答的问题，再播报任务结果。

通过任务详情的回复入口提交时，答复关联到具体任务和问题。通过聊天或语音作答且无法判断归属时，先请用户明确要回答哪一个问题。待用户任务获得有效答复后重新进入调度，在并发上限内获得执行名额后继续。

语音空闲计时只监控主对话的识别、处理和播报等交互活动。后台任务执行不占用语音忙碌状态，语音超时返回待唤醒时任务继续运行。

### 6.8 重新开始与明确退出

重新开始后，已有任务继续执行，记录和查看入口保留。任务完成时，在当前聊天区显示简短结果及所属任务，任务详情保留原始来源和完整执行关联。

明确退出时保存任务，停止可取消工作，等待当前不可取消步骤结束后退出。等待期间显示“等待当前步骤完成后退出”及所属任务和步骤，并提供撤回退出操作。保存失败时保留窗口并展示原因。宿主退出与用户主动暂停、取消分别记录，重启后依据 D-09、D-10 恢复任务。

撤回退出后恢复派发。因退出而中止的任务核对步骤后自动接续，仍在运行的步骤继续。用户主动暂停或取消的状态和在途停止意图继续按 D-10、D-45 处理。

### 6.9 失败与用户恢复

任务执行失败或运行监控发现异常时，保存具体错误并报告任务状态，提供由用户发起的继续和重试入口。在同一任务下新增执行记录，核对后从未完成部分继续。若前次动作结果无法确定，按第 6.6 节处理。

本机动作已停止或完成，但执行结果写入失败时，暂停该任务的后续派发，在界面显示保存失败原因和已知动作结果。恢复写入后，用户继续该任务时先核对上一步的实际结果，保存结果后再处理未完成部分。已有用户暂停或取消意图时，按第 6.6 节完成相应操作。

聊天回复失败时，用户点击「重新发送」，先根据原消息查询任务创建结果。若该消息已创建一个或多个任务，显示这些任务的状态。确认尚未创建时才重新处理原请求。普通聊天重发沿用 V1.0.0 规则。

## 8 数据、运行与可追溯性

任务保存创建时的输入来源，并关联来源消息、目标、当前状态、各次执行、后续输入、必要结果以及相关任务。暂停、取消、失败和恢复等状态变化需要保留发生原因，供恢复任务和查询状态使用。

任务状态和待处理工作在数据库事务中保存后交给执行器。同一输入拆出的任务及其与原消息的关联一起保存。重发沿用原请求的关联，同一输入的重复处理通过事件或消息标识及主键约束处理。暂停和取消意图独立于退出原因与动作进度保存。

派发改变本机状态的动作前，保存该步骤的待执行记录。动作停止或完成后，保存实际结果再派发该任务的下一步。工具动作结果与模型描述分别记录，状态展示以真实结果为依据。

任务与本次执行持有业务标识，用于持久化、关联和恢复。MCP 的请求、连接或协议兼容会话信息服务于工具交互，恢复依据仍是任务记录、执行记录及实际业务结果。

主 Agent 与 Worker 使用各自有限的模型工作窗口。Worker 按 D-29 回读本任务、来源对话和相关引用。任务状态、执行过程和产物引用随对话历史长期保存。生成的文件保存在用户指定的位置。

数据库结构变更采用新增迁移脚本，实现前向用户确认脚本版本编号；所有结构操作均由脚本表达。现有数据库升级后的历史、工作范围和交互设置需要通过迁移验收。

| AC-142 | 同时有两项任务在等待回答。用户先给出归属含糊的答复，再通过任务详情回复，此时执行名额已满 | 归属含糊时先澄清。详情答复仅提交到指定任务的指定问题。该任务获得答复后重新排入调度，获得执行名额后继续 |
| AC-143 | 生成原文件的最后一步执行期间收到「再加一列」 | 补充保存并可追溯。若原文件已经生成且没有下一步，告知用户原结果。明确的新增操作按关联任务处理，原文件保留 |
| AC-144 | 语音任务完成时主对话忙碌，分别验证交互保持激活和等待期间结束语音 | 结果先保存并展示。同一次交互空闲且仍激活时简要播报。结束语音或返回待唤醒时保留未读，用户再次唤醒后主动查询或要求播报才读出结果 |

验收记录分别列出自动化结果、真实语音结果和未执行项。V1.0.0 尚待完成的设备与声学实测按原清单继续跟踪。[V1.0.0 实测清单](../verification/stage-15.md#剩余实测)

## 12 架构与实现阶段需要核实的事项

- 主对话、语音流水线与业务 Worker 生命周期的实际分离位置。
- 事件、任务状态和待处理输入的存储表示。验证原消息与任务的创建事务、停止意图和各动作执行结果在中断时的恢复。
- 任务工具注册、取消、结果核对和任务范围的表达。
- MCP Client/Server 接入、GUI 线程调度、所选传输的取消行为及业务状态关联；协议与 SDK 版本在技术选型时核实。
- 主 Agent、Worker 和反馈之间的调度、顺序及资源冲突处理。
- 主对话和任务历史的有限窗口、引用读取、升级和恢复。
- 运行监控的观察信号、任务失败归因和用户可操作入口。
- 对话响应、任务派发与控制延迟、并发资源及真实语音联动的测量方法和目标。
- 各内置工具对实际结果的核对方式。Windows 应用定位与窗口识别、文件尺寸和编码的支持边界，以及同一资源的冲突判定，按真实工具验证。
- 任务数据和并发设置的数据库迁移。编写新迁移脚本前向用户确认脚本版本编号。
